## 1. 总体逻辑

### 1.1 一条链路，五个问题

用户的请求要经过：**用户的工具（Agent / SDK）→ semifly.ai 网关 → 上游供应商（KerAPI）→ 模型**。任何一环都可能出问题，所以测试围绕五个问题展开：

1. **通不通**（可用性）：Key、模型、链路是否可用。→ 采购 Key 检测、Key 巡检、运行观测
2. **对不对**（功能与兼容）：参数、格式、工具调用、思考、流式这些功能是否和官方一致。→ 功能对比、Agent 检测、兼容性矩阵
3. **好不好**（质量与身份）：是不是官方那个模型、有没有被降级。→ 任务验收、身份检测、型号对比、Agent 对比
4. **扛不扛得住**（容量与性能）：并发、首字延迟、输出速度。→ 压测
5. **算得对不对**（计量与财务）：Token、缓存、扣费是否一致。→ 逐笔交易、计量核账

### 1.2 贯穿所有测试的原则

- **以官方 API 为尺子。** 结论都是相对官方给出的：只有“官方能、我们不能”才算我们的问题；“官方也不能”是模型自身的边界。评测用的官方 Key 只存在「评测 Key」页，员工请求永远不会走它。
- **真实环境，真实计费。** 测试在生产环境进行，用的是给员工提供服务的同一套网关和同一批供应商 Key。测出来的就是用户实际得到的。
- **只记结构，不记对话。** Agent 检测和兼容性矩阵记录的是请求的“形状”（参数、工具定义、消息条数、长度），不记录内容。测试题都是极短的人造题，不含用户数据。
- **按规则判定，尽量不靠主观。** 能用规则判的（JSON 能否解析、是否调用了工具、finish_reason、用量是否自洽）一律用规则判。质量类再加盲评。
- **花钱有上限，不自动重试。** 每类测试都有调用次数或预算上限，失败不自动重试，避免“越错越花”。
- **每一步留痕。** 启动、发布、修改都写审计日志；测试记录可导出 CSV，与供应商账单逐笔核对。
- **结果不稳定的项要重跑。** 两次运行结论不同的项，重复测试，确认差异真实存在才算数。

### 1.3 用到的测试风格

| 风格 | 含义 | 用在哪里 |
|---|---|---|
| 差分测试（对照测试） | 同一请求发给两个系统，比较结果 | 功能对比、型号对比、Agent 对比 |
| 录制—回放 | 先录真实请求的结构，再脱离原客户端重放 | Agent 检测、兼容性矩阵 |
| 功能探针 | 每个探针只测一个功能点，答案短、可判定 | 功能对比、Key 检测 |
| 金标准题 | 有唯一正确答案的固定题目 | 任务验收、型号对比 |
| 盲评 | 评审者不知道哪个回答来自哪边；换位再评一次 | 型号对比、Agent 对比 |
| 阶梯加压 | 并发逐级提高，找出稳定上限 | 压测 |
| 合成监测 | 定时用人造请求检查线上状态 | Key 巡检、运行观测 |
| 逐笔对账 | 按请求号把两本账一行一行对 | 计量核账 |

## 2. 现有测试逐项说明

### 2.1 评测 Key：测试用的“尺子”

- **目的**：给所有对比测试提供基准。
- **怎么做**：每家厂商（DeepSeek 官方、智谱 GLM 国内、Z.ai GLM 国际）保存一把官方 API Key。保存时会向厂商查询这把 Key 能用哪些模型，并为每个模型登记一个“参照端点”。
- **规则**：
  - 每家厂商只有一把有效 Key，换 Key 时旧的自动停用。
  - 它是 `reference`（参照）类型，路由只会选 `supplier`（供应商）类型，所以员工请求不可能走到官方 Key。
  - 官方域名自动加入白名单，不用手工维护。
- **局限**：官方 Key 本身的额度和限流会影响对比，所以对比失败时要先看官方那一列是不是限流。

### 2.2 采购 Key 检测（上游接入 → 采购 Key）

- **目的**：确认每把供应商 Key、Key 下的每个模型现在能用，并知道各自的延迟。
- **怎么测**：
  1. 先调用供应商的 `/models` 接口，看它实际提供哪些模型。
  2. 再给每个登记的模型发一个 `max_tokens=1` 的最小请求，三个并发。
- **判定**：
  - 返回即通（绿点），失败显示红点和供应商的原始错误信息。
  - 模型按延迟从低到高排列。
- **附带检查**：
  - **重复 Key**：两把 Key 指纹相同，就是同一把，不算备用。
  - **输出上限**：`max_tokens=1` 却返回了超过 1 个 Token，说明上游不遵守输出上限。网关会自动对这个模型启用“输出保护”，详见 2.11。

### 2.3 功能对比（验收测试 → 功能对比）

- **目的**：逐项确认官方 API 能做的功能，我们这条链路也能做。这是公网实测报告 `/#realtesting` 的数据来源。
- **怎么测**：
  - 同一个请求、同样的参数，一份直接发官方 API，一份走我们的 API（网关 → 供应商，和员工拿到的完全一样）。
  - 每个“我们的产品”对照一个“官方型号”，表头两行分别标明。
- **25 项探针，8 类能力**：

| 类别 | 测试 | 测什么 |
|---|---|---|
| 基础 | 基础对话、流式输出 | 能否正常回答；流能否逐字返回并正常结束 |
| 工具调用 | 工具调用、指定工具、工具结果回传、一次调用多个工具 | Agent 的核心：会不会调用工具、能否按指定调用、能否接着工具结果作答、能否并行调用 |
| 输入与格式 | 图片输入、JSON 输出、JSON Schema 约束、停止词 | 多模态输入；结构化输出；stop 参数 |
| 思考 | 思考·低/中/高/超高、开启思考、关闭思考 | 思考强度参数和开关是否生效（用需要推理的小题，避免模型随机跳过思考） |
| 输出长度 | 输出 ≥8K、输出 ≥32K、输出截断标记 | 输出上限是否被放行；超限时 finish_reason 是否为 length |
| 长上下文 | 上下文 ≥32K、≥128K | 约 3 万字 / 12 万字的输入能否处理 |
| 对话 | 系统提示词、多轮对话记忆 | 是否遵守 system；是否记得前一轮 |
| 计费 | 流式返回用量、缓存命中 | 流结束时是否带 usage；同样的长前缀发两次，第二次是否报告缓存命中 |

- **四种结论**：
  - **一致**：官方能用，我们也能用。
  - **更多**：官方报错或不支持，我们能用。
  - **模型限制**：官方也不支持，两边一样。
  - **差异**：官方能用、我们不能。只有这一类算问题，必须修复或解释。
- **测试数据**：全部是人造短题。例如：“请按要求的 JSON 结构回复：ok 填 true，n 填 3”；长上下文用重复文本填充到目标长度。
- **最近一次结果**（2026-11-12，生产环境，260 次请求）：5 个模型 × 25 项，125/125 一致或更好，**0 差异**。
- **这套测试推动过的修复**：
  - 输出上限从 8K 放开到 32K。
  - GLM 思考强度和关闭思考自动换算成 GLM 支持的档位。
  - GLM 的 JSON Schema 自动换成 json_object 加结构说明。
  - 发现 GLM-5.3-FlashX 不遵守 max_tokens，网关加了输出保护。

### 2.4 Agent 检测（验收测试 → Agent 检测）

- **目的**：用户用的是 WorkBuddy、Cursor 这类 Agent，而不是裸 API。不同 Agent 会发出很特别的请求（参数组合、工具定义、超长 system）。我们要确认这些真实请求在每个模型上都接得住。
- **怎么测**：
  1. **录制**：员工 Key 上开一个录制会话，一次“布防”一个功能（例如“联网搜索”“读文件”）。在 Agent 里触发这个功能后，这把 Key 上收到的请求就标记为该功能。只保存请求结构。
  2. **学习**：网关已经从员工真实调用里学到的请求格式，可以直接导入成录制结果，不必人工录。
  3. **回放**：不需要 Agent，直接把录到的请求结构发给我们的每把 Key、每个模型，同时发给官方 API。
- **判定**：官方那一列能跑、我们不能，才是我们的问题；官方也跑不通，是这个 Agent 和模型本身不兼容。
- **视图**：每个产品一行，右侧是对应的官方型号；每个 Agent 版本单独记录，Agent 升级后可以重测。

### 2.5 兼容性矩阵（验收测试 → 兼容性矩阵）

- **目的**：回答“哪个工具 × 哪个选项能用”，例如“Cursor + 思考强度高 + 128K 上下文”。
- **怎么测**：网关自动从员工真实调用里学到每个工具的请求格式，包括参数、工具定义、消息条数和大小。回放时用同样的格式、同样大小的上下文，只把对话内容换成测试内容，并经过和员工一样的网关校验。
- **判定**：每个格子是回放成功、失败或“见过但未回放”。
- **扩充方法**：在某个工具里打开一个新选项正常用一次，矩阵就会多出一格，再点“回放”即可。
- **和 Agent 检测的区别**：矩阵的数据来自被动积累的真实流量；Agent 检测是主动按功能录制。

### 2.6 任务验收（验收测试 → 任务验收）

- **目的**：新接入一个型号时，先用最小成本确认它能正确答题，并且用量报得自洽。
- **4 道固定题**（规则判分）：

| 题目 | 内容 | 判定 |
|---|---|---|
| 事实与计算 | 17 × 23 | 严格等于 391 |
| 结构化 JSON | 输出 `{result:42, ok:true}` | 能解析且取值正确 |
| 中文表达 | 翻译 Hello, world! | 包含“你好”和“世界” |
| 上下文理解 | 给两座城市的代号，问乙城 | 严格等于“红星” |

- **同时检查**：
  - HTTP 状态和延迟。
  - 输入、缓存、输出 Token 是否自洽。
  - 推理 Token 是否回报。
  - 回报的型号名和请求的是否一致（防止被换成别的模型）。
  - 是否因达到上限被截断。截断的题目不据此判定模型能力，只提示调整参数。
- **成本**：每次最多 4 次付费调用，不自动重试。

### 2.7 逐笔交易（验收测试 → 逐笔交易）

- **目的**：每一次测试调用都可追溯、可对账。
- **记录内容**：
  - 时间，以及所属的供应商 / Key / 型号。
  - 验收结论和得分。
  - 输入 / 缓存 / 输出 Token（推理 Token 含在输出里，不重复相加）。
  - 延迟、预估采购成本，以及上游请求号。
- **用法**：导出 CSV（最多 1000 笔），用本台流水号、上游请求号、Key、型号和 UTC 时间，与供应商账单逐行核对。**缺少上游请求号的记录不能证明逐笔一致。**
- **常见异常标记**：
  - 上游未回报型号、回报型号与请求不符。
  - Token 或缓存计数不自洽。
  - 输出达到上限、响应无正文。
  - 超时、响应过大、网络或协议错误。
  - 费率未知。未知费率不按 0 元处理。

### 2.8a 身份检测（对比评测 → 身份检测）

- **目的**：确认供应商给的就是官方那个模型、是满血版，没有被换成更便宜的模型或量化、缩小过的版本。功能对比查不出这类问题。
- **怎么测**：和功能对比一样，同一请求一份发官方、一份走我们的 API。四项检测：
  1. **分词指纹**（最可靠）：5 段固定文字（中文、英文、代码、数字符号、生僻字和表情），比两边回报的输入 Token 数。差值全为 0 = 同一个分词器；差值固定 = 上游给每个请求加了看不见的内容（会多计费）；差值随文字变化 = 分词器不同，基本可以断定不是同一个模型。
  2. **自报身份**（旁证）：问“你是什么模型、哪家公司开发”，看是否自称同一家；同时记录响应里的型号名。
  3. **输出相似**（参考）：温度 0 的三道开放题，官方答两次作基准，比较我们和官方的字符二元组相似度。官方自己两次都不像（< 0.35）时不比较。
  4. **能力小测**（抓降级）：20 道只有一个正确答案的题（多位数计算、取余、日期、星期、进制、代码输出、逻辑排序等），要求最后一行写“答案：”，按规则判分。只比两边都答完的题；被截断或失败的不计。
- **判定**：
  - 疑似：分词差值不固定，或小测少对 ≥ max(3, 15%) 题。自报身份只作旁证：分词已一致时自称别家不作数（2026-11-12 实测，DeepSeek 官方 API 自己也会自称 OpenAI / ChatGPT）。
  - 需要关注：分词固定偏移；小测少对 2 题；相似度明显低于基准；思考长度相差一倍以上；分词不一致时还自称别家。
  - 正常：以上都没有。
- **分时段**：每次记录是高峰（工作日北京时间 9–18 点）还是低谷，历史表可以对比。
- **成本**：身份指纹每个型号 21 次调用（约 1 分钟）；能力小测每个型号 40 次（需要思考，约 5–15 分钟）。
- **局限**：同一厂商的大小模型可能共用分词器，要靠小测和型号对比区分；20 道题样本小，单次少对 1～2 题属于正常波动，要看多次趋势。

### 2.8 型号对比（对比评测 → 型号对比）

- **目的**：供应商可能提供“同名但降级”的模型，比如量化版或更小的模型。功能对比看不出这类问题，要比**回答质量**。
- **12 道题，覆盖 9 类**：
  - 计算：四则运算、应用题
  - 推理：逻辑排序
  - 结构化：信息抽取 JSON
  - 指令遵循：格式约束
  - 代码：Python 函数、SQL 查询
  - 长上下文：长文检索（大海捞针）
  - 语言：英译中、一句话摘要
  - 写作：客户说明
  - 知识：技术常识
- **三种打分方式**：
  1. **规则自动判**：有确定答案的题（如 549、JSON 字段）。
  2. **第三方模型盲评**：评审模型不知道哪边是官方。A/B 位置换过来再评一次，两次结论一致才算胜负，以消除位置偏差。
  3. **人工盲评抽查**：工作人员看到两个回答，但不知道来源。
- **测试数据**：每题带评分标准（rubric）。长文检索题把一条关键信息埋在很长的仓库日志里。

### 2.9 Agent 对比（对比评测 → Agent 对比）

- **目的**：看端到端结果，而不只看单个请求：同一个 Agent 做同一组任务，走我们的线路和走官方，最终交付是否一样好。
- **两条路**：
  - **A 路**永远是我们的线路（网关 → KerAPI）。
  - **B 路**有两种选择：
    - 官方 API：同样经网关转发到官方参照模型，两边的完整过程都能记录。
    - Agent 自带的模型：不经过我们，工作人员把最终回答贴进来。
- **专用测试 Key**：前缀为 `sf_eval_`，由工作人员持有，不向员工计费，保存完整对话，测试结束即作废。
- **评分**：
  - 评审模型盲评，换位两次。
  - 人工盲投。
  - 同时统计每条路的调用次数、Token、耗时。

### 2.10 压测（压测）

- **目的**：知道每个模型在我们这条链路上能稳定承载多少并发，并和员工真实峰值比较，判断是否需要扩容或加 Key。
- **三种负载画像**：

| 画像 | 输入 | 输出 | 看什么 |
|---|---|---|---|
| 短问答 | 一句话 | 约 60 字 | 首字延迟、排队 |
| 常规对话 | 约 2 千字 | 约 300 字 | 接近员工日常 |
| 长上下文 | 约 2 万字 | 约 100 字 | 长输入下的排队和首字延迟 |

- **怎么测**：
  - 并发按 1、2、4、8、12、16、24、32 一档一档加。
  - 全部用流式请求，记录首字延迟（TTFT）、总耗时、输出速度和报错。
- **安全阀**：
  - 最高 32 并发，最多 240 次请求，预算不超过 ¥20。
  - 某档失败率超过 20% 立即停止，单请求超时 120 秒，可随时手动停。
  - 启动前按最长回答估算最高花费，超过预算的不允许启动。
- **“稳定并发”的定义**：从第一档起连续满足以下两条的最高并发：
  - 成功率 ≥ 98%；
  - 首字延迟 P95 不超过“最轻那档 P95 的 3 倍”和“最轻那档 P95 + 2 秒”中较大的一个。
- **对照**：同一模型员工最近 7 天的真实峰值并发。

### 2.11 运行观测与持续监测（运行观测）

- **Key 巡检**（服务启动 2 分钟后第一次，之后每 30 分钟一次，也可手动触发）：
  1. 读每把采购 Key 的模型列表，和我们在售的模型对比：
     - 上游**新增**了我们已定价的模型：自动上线，并发信息邮件。
     - 上游新增了**未定价**的模型：发警告邮件，提醒人工定价后上线。
     - 上游**下架**了我们在售的模型，或 Key 不响应：发严重告警邮件。
     - 两把 Key 是同一个密钥：发警告，它不算备用。
  2. 每个模型发一个 1-Token 请求，确认能答。
  3. 发现不遵守 max_tokens 的模型，标记后由网关**输出保护**接管：
     - 对这个模型总是让上游流式返回，网关自己计数，到上限就关闭上游连接，返回 `finish_reason=length`，行为和官方一致。
     - 被截断的那次调用没有可信用量，计费等供应商日志。
     - 上游修好后，下一次巡检自动解除。
- **事件规则**：事件一直保持“打开”，直到某次巡检不再看到它。新的警告和严重事件立即发邮件给平台管理员。
- **合成测试汇总**：内部测试调用的成功率、结构正确率和异常类型。

### 2.12 路由与熔断（路由与放行）

- **主备切换**：每家供应商一把主用 Key、若干备用 Key。主用 Key 认证失败或连不上时，员工请求自动改用备用 Key。巡检会识别“名义上的备用其实是同一把 Key”这种假备用。
- **手动熔断**：任何模型都可以立即暂停，员工调用马上停止，并记录原因。
- **放行**：业务批准的目录才会发布；发布不会自动开放客户计费和调用。

### 2.13 计量核账（计量核账 → 逐笔对账 / 上游全部记录）

- **目的**：确认我们记的账（Token、缓存、费用）和供应商实际扣的钱逐笔一致。
- **怎么做**：
  1. 每 5 分钟拉取供应商（KerAPI）的用量日志。同一密钥只拉一次，避免重复记录。
  2. 按请求号把我们的记录和上游记录配对。
  3. 用上游给出的计费表达式（含工作日高峰时段 2 倍等倍率）独立复算一遍费用。计费表达式只当证据解析，绝不当代码执行。
- **结论分类**：
  - 计量及规则复算一致；
  - 有差异；
  - 证据不全；
  - 等待上游记录；
  - 请求号重复；
  - 缺少请求号。
- **边界情况**：请求恰好跨过计价时段边界的，保持“未核实”，不硬判。
- **安全**：导出和展示时，自动抹掉 Key、Token、密码等字段。

## 4. 还没有上线的测试方法

以下是业界在模型和 API 测试上常用、我们还没做的方法。每项写清楚是什么、解决什么问题，并按对我们（中转 / 网关业务）的价值标出优先级：★★★ 建议尽快做，★★ 值得做，★ 以后再说。

### 4.1 模型身份与“掺水”检测（中转业务最关心）

| 方法 | 是什么 | 解决什么 | 优先级 |
|---|---|---|---|
| 模型指纹 | **已上线一部分（身份检测：分词指纹、自报身份、输出相似）**。还可以加：用一组对特定模型有独特反应的问题（自我介绍、特定知识截止、特有的格式习惯、分词边界题），建立官方模型的“指纹”，定期比对供应商 | 供应商偷换成更便宜的模型 | ★★★ |
| 降级 / 量化检测 | **已上线（身份检测 · 能力小测，20 题）**。下一步：扩到 50 题、每天定时自动跑。定期跑固定的高难度小题集（数学、代码各 20～50 题），对比官方得分分布。分数持续偏低说明可能被量化或缩小 | 同名模型被悄悄降级 | ★★★ |
| Token 计数独立复算 | 用官方分词器（或官方的 token 计数接口）对同一输入独立计数，和供应商回报的 prompt_tokens 比较 | 用量虚报、多收钱 | ★★★ |
| 真实上下文长度 | 在 8K、32K、64K、128K 不同长度、不同位置埋“针”（Needle-in-a-Haystack / RULER 方法），看哪里开始找不到 | 宣称 128K、实际被截断 | ★★ |
| logprobs / 采样一致性 | 支持 logprobs 的模型，比较同一输入下首 Token 概率分布和官方是否一致 | 最精确的“是不是同一个模型”证据 | ★★ |

### 4.2 能力基准（公开评测集，抽样跑）

不需要跑全量，每类抽 50～200 题，定期在官方和我们这边同时跑，看差值是否稳定。

| 能力 | 常用评测集 | 说明 |
|---|---|---|
| 知识 / 综合 | MMLU-Pro、C-Eval、CMMLU、GPQA | 中文场景重点用 C-Eval、CMMLU |
| 数学推理 | GSM8K、MATH、AIME | 对思考模型最敏感，最能看出降级 |
| 代码 | HumanEval、MBPP、LiveCodeBench、SWE-bench Verified | SWE-bench 最接近 Agent 写代码的真实场景，成本高 |
| 工具调用 | BFCL（Berkeley Function Calling Leaderboard） | 函数调用的准确率：参数、多函数、并行、不该调用时不调用 |
| Agent 任务 | τ-bench（tau-bench）、Terminal-Bench、GAIA | 多轮、多工具、长流程任务的成功率 |
| 指令遵循 | IFEval、FollowBench | “恰好三条”“不超过 50 字”这类可验证约束 |
| 长上下文 | LongBench、RULER、Needle | 长文理解和检索 |
| 事实性 / 幻觉 | SimpleQA、TruthfulQA | 是否胡编 |
| 开放式对话质量 | MT-Bench、Arena-Hard、AlpacaEval（模型评审） | 主观质量，用强模型做评审 |

优先级：★★。建议先从 GSM8K/MATH 子集 + BFCL 子集 + IFEval 子集做起，成本低、信号强。

## 6. 术语

- **TTFT**（Time To First Token）：首字延迟，从发出请求到收到第一个字的时间。
- **TPS**（Tokens Per Second）：输出速度。
- **P95**：95% 的请求都不超过这个值。
- **finish_reason**：回答结束的原因。`stop` 表示正常结束，`length` 表示达到输出上限被截断，`tool_calls` 表示要调用工具。
- **参照端点（reference）**：官方 API 的测试入口，只用于对比，不参与路由。
- **盲评换位**：评审时隐藏来源，并把 A/B 位置对调再评一次，两次一致才算数，用来消除评审模型偏爱某个位置的倾向。
- **输出保护**：上游不遵守 max_tokens 时，网关代为计数并截断，保证行为和官方一致。
