# 资金计费与采购流程

## 先分清六种金额

| 概念 | 表示什么 | 不能混同 |
| --- | --- | --- |
| 支付订单 PaymentOrder | 客户打算支付的金额与支付状态 | 不等于已经到账 |
| 实付消费额度 PaidCredit | 已确认款项对应、尚可消费的额度 | 不等于全部已赚取收入 |
| 赠送额度 PromotionalCredit | 平台营销预算授予的有限消费权益 | 不等于现金或可退本金 |
| 消费费用 UsageCharge | 按用量和当时价格计算的客户费用 | 不等于供应商成本 |
| 企业应收 Receivable | 按合同应由企业支付的款项 | 不等于客户的现金余额 |
| 佣金应付 CommissionPayable | 已满足结佣条件的渠道债务 | 不等于客户消费额度 |

财务记账与收入确认科目由会计按实际合同和准则确认。产品设计至少保证充值、消费、退款、应收、供应商应付和佣金应付可分别追踪；不将“充值总额”直接展示为“利润”。

## 唯一业务账本

以 PostgreSQL 的业务账本作为平台经济效果的权威记录。网关可保留限流、预算等运行状态，支付机构也保留支付和结算记录，但它们不能各自独立改写客户的业务余额。

采用平衡分录、不可变交易和冲正方式。每笔账本交易记录法人、区域、币种、业务事件、外部凭证及分录。余额由分录推导，缓存可重建。交易级唯一约束防止重复入账；已记账错误以反向分录和新分录更正。

平台内保证同一业务操作只产生一次预期经济效果。外部供应商是否支持请求幂等要单独验证，不能据此承诺跨供应商“端到端绝对只执行一次”。

## 货币精度

支付与发票按相应货币最小单位和税务规则处理；API 用量计费保留更高精度，例如定点微单位或 decimal 类型。禁止二进制浮点直接累计金额。每次调用不强制向上取整到一分，应先以高精度累计，再按明确规则在账单行或账期结算。

人民币与美元分别记账，不跨币种直接相加。供应商成本币种、客户售卖币种和报表币种是三个维度。成本换算保存汇率来源、日期及快照；更新汇率不重算历史账单。

## 充值支付流程

1. 创建待支付订单，固定客户、地区、币种、金额及适用商品。
2. 调用支付适配器，客户完成付款。
3. 后端验证支付机构签名，核对订单、商户、金额及币种。
4. 将事件可靠落库；在同一数据库事务中确认支付状态、写账本和写待处理事件。
5. 异步更新通知与网关授权缓存。客户可用额度以业务账本结果为准。
6. 重复或乱序回调不会重复加钱；存在歧义时主动查询支付机构。

浏览器跳回“成功页”不是到账证据。Stripe 明确说明事件可能重复、可能乱序；出站支付请求的幂等键与入站回调的去重是两个机制。[S10](11-sources.md#s10)[S11](11-sources.md#s11)

支付手续费、实际结算净额和客户购买额度分别记录。客户付 100 元、支付机构扣费后到账 99 元，并不意味着客户只获得 99 元额度，除非产品明确这样约定。

## API 请求与费用流程

1. 验证 Key、组织、区域、模型权限和限流。
2. 冻结本次模型/价格/优惠/供应商选择规则的版本。
3. 以输入用量估计、最大输出限制和价格规则计算保守的费用上限，原子预占客户预算。
4. 在准许的供应商通道中选路；持久记录请求已授权，再向上游发送。
5. 按流式或普通响应交付，收集实际 usage、上游请求标识和尝试记录。
6. 用真实计量结算费用，释放剩余预占；供应商成本独立记录。
7. 异常或用量不明的请求进入待核实队列，保留预占到明确的处理期限，超期升级人工；不能无限冻结，也不能默默重复扣款。

输入 token、缓存命中、缓存写入、输出 token、推理 token 的含义按实际供应商协议映射。推理 token 若已包含在输出用量中，不再重复收费。阶梯价、长上下文加价和附加工具费用分别建计价维度。

输入预估不是最终收费依据。流中断、客户取消、上游已经生成内容时，可能发生真实供应成本。平台须公布这些场景的客户计费规则，并保留证据；不能宣称所有非 200 响应都没有成本。

输入估计也不天然构成严格费用上限。首期只销售能够可靠限制计费上限的能力；可提前发现需要追加预算时先追加预占，追加失败则限制后续可控消耗。已经发生且无法避免的差额进入公开的异常结算规则，不在最终扣款时默默透支。

预占应在同一本地事务中同时占用付款账户资金或信用，以及适用的 PO、项目、Key 和分销子账户预算。任一限制不足全部回滚；子预算是限制，不产生第二份资金。

每次上游重试有独立 attempt_id；客户端一次逻辑请求有 request_id。对客户只按合同认可的经济事件收费；平台额外重试造成的供应商成本可能由平台承担。

每个上游尝试保存实际采购方案、价格版本、币种、计量规则及成本记录，区分暂估、确认和对账状态。一个请求的采购成本汇总所有真实尝试，不能只留最后成功通道；客户退款也不自动冲回供应商成本。

推理接口需明确客户端幂等能力。建议支持作用域为组织和接口的客户端幂等键，并保存请求摘要、状态及有效期；同键不同内容返回冲突，同一已识别请求不重复派发。若不保存响应正文，则对完成后的重复请求返回状态信息，不承诺重放完整输出。首期若暂不支持该能力，必须明示重发是新请求；费用事件去重不能冒充客户端重试去重。

## 价格优先级

建议顺序为：已签企业合同价或渠道批发价 → 经审批的专属方案 → 区域公开零售价，再判断允许叠加的活动优惠。任何优惠均检查适用模型、币种、期间、次数和毛利下限。

价格变更创建新版本和生效时间。供应商同步获得的新报价先进入草稿，审核后发布；历史请求保留原价格快照。未配置价格的商品不可直接成为生产可售项。

## 个人与企业采购

个人默认预付。企业首期也允许预付，后续按信用审核开启账期。企业采购流程为：报价 → 合同/订单 → 客户 PO → 企业内部与平台审批 → 开通限额 → 产生用量 → 形成对账单和账单 → 按地区开具税务文件 → 回款核销。

PO 是客户采购授权，不是到账证明。PO 编号、预算、期限、适用项目和合同版本都要保存。调用预占和已发生费用都占用采购预算；不能等到开票才发现超出 PO。

净 30 天等账期是协商配置，不是所有企业的默认权利。支持部分付款、多笔付款核销一张账单、一笔付款分配多张账单、贷项与争议金额、逾期提醒和信用额度停用。

BillingInvoice 是商业应收账单；TaxInvoice 是税务发票或税务文件。中国税务发票与美国 invoice/receipt 使用不同适配器，编号和状态不合并。中国红冲及美国贷项/退款关联原单，具体税务处理由本地主体确认。[S07](11-sources.md#s07)[S13](11-sources.md#s13)

## 退款与拒付

区分未消费本金退款、已消费服务退款、支付拒付与赠送额度撤销。退款前检查可退来源、历史消耗、发票状态、在途请求和已有退款；预留可退金额，防止退款同时继续消费。

支付机构退款确认后写相应账本记录。退款失败进入可恢复状态，不能先删支付记录。赠送额度不能按现金退款；已消费争议按服务协议和证据处理。拒付可能晚于佣金付款，因此需要佣金观察期、准备金或追回安排。

每笔消费保存从实付额度批次、赠送权益批次扣取的分配记录，实付批次关联原支付订单。扣减顺序、适用范围及有效期采用版本化规则。退款、拒付和佣金使用这份已冻结分配，不从当前余额倒推历史。

拒付按争议中、胜诉和败诉分别处理。已消费服务对应本金被扣回时，按协议和财务政策形成客户欠款或平台损失，并处理剩余额度及停用状态；拒付费单列，不删除原支付、消费或佣金记录。

## 三方和四方对账

每日对比客户支付与平台订单、平台记账与支付结算、平台 usage 与供应商 usage/账单、渠道佣金与真实回款。差异分为时间差、价格版本、计量差、退款拒付、币种换算、遗漏和重复。

对账结果必须有负责人、状态、处理证据和更正关联。对账服务发现问题后不能任意改余额；它创建修正工作流并由授权人员审核。

## 毛利示例

以下数字仅用于说明计算关系，不是模型报价，也不是获利预测。

客户充值 100 元。本次用量按公开价格为 100 元，打九折后实际消费 90 元；客户剩余实付额度 10 元。假设供应成本 65 元、该合格消费返佣 5% 即 4.50 元、分摊支付成本 1 元，则这笔服务的贡献毛利为 90 - 65 - 4.50 - 1 = 19.50 元。

这 19.50 元尚未扣除服务器、人员、其他运营成本和适用税费。未消费的 10 元不能再次作为利润；佣金基数为本例已收款且已消费的 90 元，不是充值 100 元。赠送额度面值不作为收入，也不直接重复计为费用；其对应真实供应成本和额外营销支出分别归集，避免重复扣除，赠送部分不计佣。
