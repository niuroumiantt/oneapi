# 用户企业与渠道关系

## 人与组织分开

User 表示一个自然人的登录身份。Organization 表示个人工作区或企业组织。Membership 表示这个人在某组织的角色。Project 表示组织内一个应用或成本中心。BillingAccount 表示某区域签约主体、币种和付款方式下的计费账户。

同一个人可以同时拥有个人工作区、加入两家公司、管理多个项目；这些组织的 Key、额度、账单和成员彼此隔离。不能用 User 上的一个 is_enterprise 字段承载全部企业逻辑。

个人工作区与企业组织可以共用“项目、Key、用量”能力。企业额外拥有采购、组织成员、分部门预算、合同及账期能力。企业也可以预付费，企业认证不自动授予信用额度。个人有适用开票需求时也应支持，不能把“发票”只理解成企业按钮。

## 区域身份与计费账户

统一登录体验表示一致的交互和接口，不要求所有地区共用同一个身份数据库。首期采用地区独立的身份实例或租户、会话域、会员信息和计费账户。后续跨区账号关联只传必要标识，并评估合法依据与告知要求。

用户选择美国区，不等于中国账户的余额、合同或数据自动迁移。前台明确显示当前区域、签约主体和币种；换语言只改变文案，换区域需要进入相应账户流程。IP 可以用于风控，不能独自决定客户的合同和税务身份。

## 权限模型

| 主体 | 建议角色 | 允许的主要操作 |
| --- | --- | --- |
| 企业客户 | owner、admin、developer、billing、viewer | 管成员、开发调用、财务管理或只读，分别授权 |
| 采购联系人 | procurement | 查看报价合同、提交 PO、采购审批，不必拥有生产 Key |
| 平台员工 | operations、finance、finance_approver、supplier_manager、support、auditor | 按岗位执行和审核业务 |
| 渠道伙伴 | affiliate、sales_agent、distributor、master_distributor | 按具体合作协议及授权范围启用 |
| 机器身份 | service_account | 只在指定组织、项目和接口范围内工作 |

权限以“动作 + 资源 + 范围”表示，例如 invoice.read:organization、supplier_cost.update:region、refund.approve:region。后端校验租户、地区和授权，前端隐藏按钮仅作为体验辅助。

员工身份与客户身份分开管理。员工默认强 MFA；离职立即撤销会话和业务权限。退款、提高信用额度、修改采购付款账户和高额佣金付款设置发起与审核分离。紧急权限有时限、理由和审计记录。

## 四种渠道角色

历史截图明确区分以下四种角色，本版继续采用这一业务结构。

| 角色 | 客户合同与付款关系 | 收益方式 | 平台权限 |
| --- | --- | --- | --- |
| 推广员 Affiliate | 客户直接向平台购买 | 符合规则的推荐佣金 | 推广链接、归因和自身佣金明细 |
| 代理商 Sales Agent | 通常由平台签约收款，代理协助销售 | 协议销售佣金或服务费用 | 客户报备、授权报价、销售进度及有限客户信息 |
| 分销商 Distributor | 平台向分销商批发；分销商可按合同向其客户销售 | 零售价与采购价之差 | 批发目录、自己的客户、子账户预算、结算单 |
| 区域总代理 Master Distributor | 按区域和渠道合同管理下级 | 经审查的渠道服务收入，涉及下级交易分成另行评估 | 范围有限的渠道管理和协议授权 |

这是产品定义，不是任何地区的法律身份认定。不同合同安排需对应实际消费者责任、开票主体和数据处理关系。

一家公司可有多项渠道资格，但资格属于合作协议，不直接等同员工权限。推广员不能查客户提示词、Key 或完整发票；代理商只能查看其授权客户；分销商不能看到其他分销商价格和客户。

首期推荐只做单层；区域总代理的数据模型预留，自动多层分佣延后。分成必须关联真实服务交易，不能按加入人数、入门费或发展下线支付收益。渠道深度、总分成上限、适用地区和是否允许下级分销都要在协议和系统配置中限定。

区域总代理首期只预留渠道管理关系，不默认取得下级交易抽成权。真实交易并不使层级计酬当然合法；任何涉及下级销售业绩的收益安排，都须按具体地区、组织结构和合同单独评估。[S06](11-sources.md#s06)

## 分销额度如何管理

分销商购买批发服务后，可给自己的子客户分配使用预算。子客户预算是授权额度，不能凭空增加平台已经收到的现金，也不能与分销商主账户余额重复计入可用资金。

建议平台只向分销商开一份批发账单；分销商自己的零售收款和发票由相应合同安排负责。若以后平台代分销商向最终客户收款，需要另行设计多方收款、清分、退款与税务，不沿用首期的普通预充值逻辑。

额度分配、调用消耗、供应商费用和分销商应付通过同一请求标识关联。客户归属变更按生效时间执行，历史账单不回写。

## 推荐码与优惠码

ReferralCode 用来回答“是谁介绍的”；Coupon 用来回答“优惠多少”。一个展示码可以关联两套规则，但数据对象和账本效果必须独立。

建议首版采用有效推荐首次确认绑定，固定归因窗口。具体窗口长度、佣金期间和折扣比例列为待决定项。企业代理已经批准的客户报备，优先于后来输入的普通推荐码；换归属需要业务审批。

规则应明确：只限新客户还是所有客户、允许哪些区域/模型/币种、优惠上限、是否和合同价叠加、有效期、每人使用次数，以及退款和关联账号处理。首版默认企业合同价与普通优惠不叠加，白名单例外单独批准。

## 佣金生命周期

候选归因 → 合格已消费金额确认 → 待结算 → 经过争议观察期 → 审核通过 → 已付款。期间可以进入冻结、驳回或冲回状态。

建议基于已收款且实际消费的净服务金额计佣，排除税款、赠送额度、退款和不计佣商品。充值不立即全部产生佣金。企业账期收入待实际回款分配后再结佣。具体返佣税务、资料要求和付款期限由协议与当地规则决定。

平台侧推荐佣金、代理佣金及批发折扣是否叠加，由渠道方案规定，并设置平台成本上限。分销商自己的零售毛利独立核算，不记作平台佣金；平台只按合同核算批发收入及适用折扣。退款后通过冲回记录调整；已经付款的佣金进入追回或后续抵扣流程，不能删除历史记录。

美国区推广中心提供与推广内容同语言、紧邻推荐内容的利益关系披露文案，并在渠道协议、物料审核和抽查中管理。佣金、免费额度或折扣构成的利益关系，不应只藏在个人资料或条款页面。[S26](11-sources.md#s26)
