# 统一账户、后台分工与付费用户面板方案

状态：**执行中**。2026-11-10，基于 `origin/main` 的代码核对。第 0 节是用户确认的最新决定，与后文冲突时以第 0 节为准。

## 0. 最新决定：三个面板、两套极简权限

| 面板 | 使用者 | 职责 |
|---|---|---|
| Token 面板 | 所有个人和企业用户 | 管理、观察、更新自己的模型使用，以 `#personal` 为模板 |
| 商务后台 | 仅本公司 | 上游、模型用量、客户、工单、供应商、财务 |
| 技术后台 | 仅本公司 | 接入、验收、对比、压测、观测、服务器 |

**Token 面板权限只有管理者和成员。** `owner`、`admin`、`billing` 都是管理者，看全公司并管理员工和额度；其余是成员，只看自己。企业至少保留一位管理者。个人账号就是自己的管理者。第 4.5 节的细分角色矩阵作废。

**后台权限只有两个开关：商务、技术。** 第 8 节的动作矩阵暂不实施，待业务需要时再细分。后台继续使用公司账号登录和 MFA，不与客户登录合并。Token 面板顶部的切换入口只是链接，按邮箱匹配有效后台员工显示，不授予任何权限。

**2026-11-12 更新：商务后台重组，后台增加第三个开关“财务”。** 商务后台改为 5 组 12 页：总览（老板驾驶舱）、财务（经营损益、收款与退款、发票、上游付款）、供应链（上游供应商、客户、企业认证审核）、产品（产品与运营、促销与折扣）、客户支持（工单与反馈、快捷问答库）。收入、成本、毛利、发票和退款只对打开财务开关的员工和平台管理员可见，接口按同一规则校验。供应商和客户有不可变编码（`S26-001`、`E26-0001`、`P26-00001`）。折扣授权本期只是台账，不参与扣费。第 7 节的标签表以此为准，细节见 `docs/handoff/business-console-redesign.md`。

**2026-11-13 更新（负责人决定，尚未实现）：** 对公转账入账采用「财务登记 + 第二人复核后入账」；现金扣费接入折扣时只取对客户最便宜的一条授权，不允许叠加。见 `docs/handoff/business-console-redesign.md`「已定（2026-11-13）」。

**不再保留单独的企业页面。** 企业空间用同一个面板，只多“员工”和“全公司用量”。公司额度属于企业空间，个人空间只显示一行提醒。

实施结果（2026-11-10）：

1. 权限收敛、身份显示、顶部切换：已上线。
2. Token 面板合并、全公司用量、员工管理：已上线。
3. 后台：商务、技术两个开关，商务 7 个标签，技术 9 组标签，路由熔断和预算内压测。放行沿用现有“验收交付、发布与下架”，没有新建第 5 节的完整通道状态表。
4. 个人升级企业：申请、人工审核、一次性转换。

与第 4 节的差异：个人账户没有写入 `organizations`。升级通过时创建企业、把现金账户转给企业，并永久关闭个人空间，用户可见行为相同，迁移更小。未做统一的 `api_keys`、`usage_calls`、`member_budgets`，也未上传证照文件。

仓库：`oneapi` 是唯一的线上和开发仓库，`openapi` 已停用（第 10 节）。

## 1. 目标与边界

要解决三件事：

1. 个人和企业从“两个并行空间”改为“一套模板”。企业账号在个人账号全部功能之上附加企业功能；个人可升级为企业，企业不可降级。
2. 理清后台技术平台和后台商务平台的目录、权限和业务流程。
3. 以 `#personal` 为起点，重新设计付费用户面板。

本方案不包含：开通微信、支付宝收款，确定客户售价，确认 KerAPI 合同价，多地区身份拆分。这些依赖继续按现有文档推进。

## 4. 统一账户模型

### 4.1 概念

- **登录身份（User）**：一个自然人，邮箱登录。不变。
- **账户（Account）**：资金、Key、用量和账单的归属单位，等级为 `personal` 或 `enterprise`。
- **成员关系（Membership）**：某人在某账户里的角色。个人账户只有所有者一人。
- **平台员工**：继续使用独立的 Authentik 身份，与客户身份完全隔离。

一个人可以有一个个人账户，同时是多家企业的成员，彼此资金和 Key 隔离。升级后，此人的个人账户变成企业账户。

### 4.2 数据模型

沿用 `organizations` 作为账户表，不新建。`memberships`、邀请链接、加入申请和审计已经都引用它，改动面最小。

| 表 | 变更 |
|---|---|
| `organizations` | 增加 `tier`（`personal`、`enterprise`）、`upgraded_at`。每个用户一条 `personal` 记录，用部分唯一索引保证 |
| `organizations` 约束 | 触发器拒绝 `enterprise` 改回 `personal` |
| `memberships` | 不变。个人账户写入一条 `owner` |
| `billing_accounts` | 回填 `organization_id` 后删除 `owner_id` 和互斥约束。账户 `id` 不变，`billing_ledger` 不改动，仍保持只追加 |
| `account_upgrade_requests`（新增） | 账户、提交人、企业全称、统一社会信用代码、证照文件引用、状态、审核员工、审核时间、驳回原因 |
| `api_keys`（新增） | 账户、创建人、名称、哈希、尾号、允许模型、消费上限、状态。替代 `pilot_api_keys` |
| `usage_calls`（新增） | 账户、成员、Key、模型、通道、状态、Token 明细、预留、实扣、结算来源、上游请求号。替代 `pilot_calls` |
| `member_budgets`（新增） | 账户、成员、预算上限、已用。企业功能，“每人 10 元”是它的一种用法 |

### 4.3 金额精度

这是必须在实现前定下来的规则。现金账本单位是分，而 KerAPI 单笔实扣可低至 0.000126 元。

- 单笔实扣记在 `usage_calls`，精度 12 位小数。
- 现金账本按账户累计，满 1 分才写入一条 `usage` 流水，余数结转，不四舍五入丢失。
- 公司发放的内部额度不进入现金账本，不可退款、不可提现。扣费优先级为先内部额度，后现金。
- 调用前按上限预留，上游账单到达后按实扣结算。这部分沿用员工额度分支已测试的逻辑。

### 4.4 升级流程

`personal` → 提交资料 → `审核中` → 通过 → `enterprise`。驳回时仍为 `personal`，可修改后重新提交。

- 审核中账户功能不受影响。
- 通过时在一个事务内完成：更新等级、写审计、登记企业信息。余额、Key、用量不移动。
- 现有 Key 继续有效，归属仍是这个账户。
- 企业代表人可以转交，但企业至少保留一位有效所有者（沿用现有规则）。
- 注册入口 `enterprise-register` 保留，内部等于“注册个人账户并立即提交升级申请”。
- 关闭 `POST /api/platform/organizations` 直接建企业的能力。

### 4.5 功能模板

后端用一张能力表统一判定，`/api/platform/me` 返回当前账户的能力，前端导航按它渲染。接口必须用同一张表校验，不依赖前端隐藏。

| 模块 | 个人所有者 | 企业所有者 | 企业财务 | 企业成员 |
|---|---|---|---|---|
| 概览 | 有 | 全企业 | 全企业资金 | 本人 |
| 模型 | 有 | 有 | 只读 | 按授权 |
| API Key | 有 | 全部 | 无 | 本人 |
| 用量 | 有 | 全企业，可按成员、部门 | 全企业 | 本人 |
| 账单与充值 | 有 | 有 | 有 | 无 |
| 支持工单 | 有 | 有 | 有 | 有 |
| 安全设置 | 有 | 有 | 有 | 有 |
| 成员与角色 | — | 有 | 无 | 无 |
| 预算分配 | — | 有 | 有 | 查看本人 |
| 发票、合同、对公转账 | — | 有 | 有 | 无 |

前端路由统一为 `#w/<账户ID>/<模块>`，`#personal`、`#organization/<ID>` 等旧地址跳转到新地址。顶部的空间切换器列出此人所有账户。

### 4.6 数据迁移

分步进行，每步可回滚：

1. 生产库备份，在恢复出的临时库上完整演练。
2. 增加字段和新表，不删除旧字段。

## 5. 供应通道：两个平台的共同主线

**通道**是“上游供应商 + 一枚 Key + 一个模型”，在现有 `supplier_lab_endpoints` 上增加状态，全系统只有一条记录。两个平台看同一个状态，各自负责不同阶段。

| 状态 | 负责方 | 进入下一步的条件 | 产出证据 |
|---|---|---|---|
| 已录入 | 技术 | Key 加密保存，归属供应商明确 | 凭据指纹 |
| 已探测 | 技术 | 目录可读，型号存在 | 探测记录 |
| 验收中 | 技术 | 通过协议、能力、计量关卡 | 测试包版本、逐笔记录 |
| 已对比 | 技术 | 完成与官方或其他上游的对比 | 质量、延迟、成本结果 |
| 已压测 | 技术 | 得到并发、TPM、429 阈值 | 受控压测报告 |
| **技术放行** | 技术 → 商务 | 提交放行单 | 见下 |
| 待定价 | 商务 | 采购价、售价审批通过 | 价格版本 |
| 已上架 | 商务 | 进入客户目录，路由生效 | 上架记录 |
| 运行中 | 技术观测，商务经营 | 持续监控 | 健康与用量 |
| 降级或暂停 | 技术可直接触发 | 恢复须重新验证 | 事件记录 |
| 已下架 | 商务 | 提前通知客户 | 下架记录 |

**放行单**是两个平台之间唯一的交接物，取代现有 `handoff` 和 `releases`，内容包括：测试包版本、已验证能力清单、容量上限、采购费率版本、已知限制、有效期。

规则：

- 放行单过期或上游型号发生变化，通道自动退回验收，商务同步收到提醒。
- 商务不能修改技术结论；技术不能定价。
- 故障时技术可直接暂停通道，无需商务审批，事后补记录。
- 未测能力显示“未知”，不得上架承诺。
- 供应商主数据合并到 `suppliers`，由商务维护，技术只维护其下的 Key 和通道。

## 6. 后台技术平台

定位：API 进来之后，如何验收、验证、比较、压测和观察，以及服务器状态。

| 标签 | 任务 | 来源 |
|---|---|---|
| 待办总览 | 今天要处理什么：验收过期、异常通道、待放行、告警 | `supplier` |
| 上游接入 | 录入和轮换 Key、发现型号、登记费率 | `suppliers` `credentials` `models` |
| 验收测试 | 运行测试包、三道关卡、查看逐笔证据 | `tests` `transactions` |
| 对比评测 | 同模型跨上游比较，发现型号漂移 | `compare` |
| 压测 | 限定预算下测并发、TPM、429、突增 | 新增 |
| 运行观测 | 每通道成功率、首 Token、P95、错误码、上游余额 | `monitor` |
| 路由与放行 | 权重、备援、熔断、提交放行单 | `handoff` `releases`，路由新增 |
| 计量核账 | 逐笔 Token 与金额，和上游日志对差异 | `billing` `upstream` |
| 服务器 | 主机状态、版本、证书、备份、云资源账单 | `servers` |

压测会产生真实费用，必须先设预算上限，由技术负责人发起，结果标注样本量和时间窗。

上游 Key 明文任何角色都不可见。所有写操作进入审计。现有 `operations`、`supply`、`finance`、`support` 和 `technical_access` 按此表映射，迁移时逐人确认。

## 9. 付费用户面板

设计原则：先回答用户最关心的四个问题：**钱够不够、现在能不能用、钱花在哪、出了什么问题**。

一级导航只保留左侧栏，取消顶部重复标签：概览、模型、API Key、用量、账单、支持、设置。企业账号在同一导航里增加成员、预算、审计。

### 各页职责

| 页面 | 内容 |
|---|---|
| 模型 | 目录、筛选、价格；点选后在右侧展开接入信息，不占首屏 |
| API Key | 接入地址、Key 列表（名称、尾号、最近使用、消费上限）、新建、停用 |
| 用量 | 按时间、模型、Key 筛选；Token 与费用趋势；逐笔明细；导出 |
| 账单 | 余额、充值、流水、发票入口 |
| 支持 | 提交工单、查看进度、常见接入问题 |
| 设置 | 账号安全、通知阈值、升级企业入口 |

### 显示规则

- 可用余额向下取整，不高估。结算中的金额单独显示。
- 删除没有数据来源的占位字段，如“项目”“协议”。
- 零数据时显示下一步动作（充值、新建 Key），不显示空表格。
- 状态绿灯注明依据和时间，不暗示长期 SLA。
- 不向客户显示采购价、供应商名称和上游错误细节。
- 企业成员看到的是自己的预算和用量，看不到企业资金。
- 手机宽度下改为单列，按余额、需要处理、接入、趋势排序。

## 10. 仓库职责

- **oneapi**：唯一的客户账户、计费、Key、后台系统。
- **openapi**：退回为本地模型路由工具，停止发展账户、门户、Stripe 功能。现有代码暂留，不删除，单独评估清理。

## 11. 主要风险

| 风险 | 控制措施 |
|---|---|
| 迁移损坏资金数据 | 账本不改动、临时库演练、迁移前后核对总额 |
| 升级不可逆，误操作无法撤销 | 人工审核、二次确认、明确告知不可降级 |
| 通道状态与实际路由不一致 | 路由只读取状态表，不另存开关 |
| 上游账单延迟造成超支 | 调用前预留，账单到达后结算 |
| 单文件前端继续膨胀 | 模板改造时按模块拆分 `web/identity.js` |
| 后台 iframe 分隔限制联动 | 重组时合并到同一外壳，或保留 iframe 并统一路由，实施前评估 |

## 13. 验收场景

1. 个人账户升级后，账户 ID、余额、Key、历史不变，Key 继续可用；数据库层面无法降级。
2. 未审核通过的账户拿不到企业功能，直接调用企业接口返回 403。
3. 企业给每位成员分配 10 元；成员登录可见，自助生成 Key；并发调用不超支；离开企业后 Key 立即失效。
4. KerAPI 单笔金额累计后，现金账本与逐笔合计相差不超过结转余数。
5. 一条新 Key 从录入走到上架，每一步在两个平台状态一致，缺证据无法前进。
6. 放行单过期或型号变化后，通道自动退回验收，商务收到提醒；技术可直接暂停通道。
7. 商务平台能回答：共几个上游、各模型是否正常、各用了多少、哪些大客户需要关注；技术权限账号不能定价，商务账号看不到技术证据的敏感字段。
