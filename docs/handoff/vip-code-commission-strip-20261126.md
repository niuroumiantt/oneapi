## 用户决定与本次实现

用户认为预计佣金、已解锁、可提现分成三条容易混淆，要求显示终端客户扫码实付，每个推广码支持同样数据，优先一根长条。

- 概览汇总所有码；推广码页每码一行，保留名称、码、折扣、状态、复制付款链接和二维码。
- 每码显示客户累计实付、实付已消费、预计佣金；有退款时单列已退款。
- 长条只分解同一佣金总额：待解锁 = 预计 − 解锁；待结算 = 解锁 − 可提现 − 提现中 − 已提现。后两段有金额才出现。
- 条内均为税前金额，提现到账净额仍以结算单为准。
- 当前归属记录区分推广码，不区分二维码扫码与付款链接入口，界面明确两者都计入。
- 自用码不产生佣金，指向充值与账单，不展示虚假的推广实付零额。
- 手机或短屏每页一条，中等屏两条，大屏三条；保留分页，不裁剪数据。

## 后端数据

`GET /api/cw/me` 使用一个 SQL 快照取得各码累计实付、消费、预计、解锁、可提现及新增 `refunded_fen`、`payout_pending_fen`、`paid_out_fen`。总计从同一结果按 BigInt 求和。

提现占用根据未释放的 payout items 和 requested/approved/paid 状态归属到原推广码，不依赖最近 100 条提现列表。失败/拒绝释放后不会继续计入提现中。退款只取已记账 refund events，重复通知不重复计数。不改变支付、佣金计算或提现政策，无数据库 schema 迁移。
