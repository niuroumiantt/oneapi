# 设计基线与产品定位

版本 0.3　日期 2026 年 11 月 6 日　状态 首期需求已重排，具体技术及商业规则仍按下文区分确认与建议。

当前研发入口：[五条并行工作线](phase-1/00-priorities.md)。

本设计用于把模型 API 买卖平台的商业逻辑、软件边界和实施顺序固定下来。它依据本轮用户描述及两张历史截图重建，不声称恢复了丢失的聊天原文。仓库为 niuroumiantt/oneapi，仓库名称不代表最终品牌，也不代表已经选择同名开源网关。

## 已确认的要求

- 一个产品面向中国和美国两个市场，设计时考虑两地合规。截图补充确认先从中国市场开始。
- 首批模型家族是 DeepSeek 和 GLM；实际模型版本、供应商通道与商业授权在接入时确认。
- 覆盖上游供应商及质量管理、模型市场、统一登录、个人付费、企业采购与 PO、账单发票、客户控制台、员工后台。
- 推广员、代理商、分销商、区域总代理具有不同商业关系；推荐码可关联优惠和返佣。
- 五条优先工作线为登录、模型广场与 Agent 接入、地区支付、线下促销码与返佣、供应商与供应产品；有效活动面向符合条件的新老客及全部启用登录方式。
- 供应管理包含如何获取 API 资源、采购产品与价格、计量计费、资金/额度与容量、需求、质量、断线及持续稳定供应；首期具备内部管理能力。
- 中国区阿里云、海外区 AWS，各自独立域名，共用核心代码并自动发布地区版本；两区工程从首期同时建设。
- 代码用途清楚，命名可读，成熟功能优先复用。
- 前台简洁精致、偏苹果风格、增加适量色彩；管理后台信息密度高、操作效率高。

## 建议的商业起点

首版采用平台以自身名义销售模型 API 服务的模式。平台与供应商签采购和服务协议，对客户承担自己的产品、计费、售后与退款责任。模型市场允许客户选择服务，但供应商暂由平台审核接入。第三方卖家自行入驻、直接向买家销售并由平台代收分账，是另一阶段的交易结构。

这能让首期清楚回答四个问题：客户向谁购买，供应商向谁交付，谁开具账单，谁处理退款争议。平台是否属于交易记录商户，应依据实际合同及客户认知确定，支付配置随后匹配，不由某个支付接口自动决定。[S08](11-sources.md#s08)

产品的价值来自模型选择、稳定接入、真实可核查的用量、企业采购便利和渠道服务。供应商的零售价格并不保证给平台留下利润。商业可行性要同时验证批量采购价、真实客户用量、收款费用、失败调用成本和服务成本。

## 第一版商业边界

首期销售按量计费服务，允许预付消费额度；企业可在审核后获得合同额度或账期。保留以后增加订阅、专属容量、承诺消费合同、私有部署和增值支持的空间。

平台消费额度用于购买本平台服务。首期不设计客户互转资金、跨币种余额兑换、通用钱包、礼品卡交易或任意提现。未消费款退款和已获批佣金付款分别处理。实际预付安排仍需支付机构与法务确认，不因采用这一产品限制就自动免除监管义务。[S09](11-sources.md#s09)

不把供应商公共 API Key、个人订阅账号或未经授权的中转服务作为货源。模型权重的开源许可与第三方 API 转售合同分别核查；能调用某个模型，不等于可以按任意方式、向任意国家再售。

## 一套产品与区域运营

建议共用产品定义、源代码、设计系统和测试用例，按中国区、美国区分别部署涉及客户数据、支付和推理的数据面。区域各自配置合同主体、商户、币种、价格、税务、日志、供应商与权限。是否采用两家公司、两家关联公司或其他合法安排，需要根据实际经营条件决定；本设计不把“两家公司”当作统一法律结论。

两区工程建设从首期并行推进，各区商用开放以相应资格、供应、支付和质量验证为门槛。一个模型家族可以展示在产品目录中，但它的某条区域销售服务必须先经过授权、数据路径、主体及行业限制审核。

## 版本管理约定

需求、设计建议、已决定事项分别记录。没有确认的折扣比例、返佣比例、品牌名、具体域名和上线日期不写成既定事实。每次确定重要业务规则后更新对应文档和决策记录，再提交 GitHub；进度说明要带实际提交记录。

公开仓库只保存可公开的设计和代码。真实供应商协议、客户材料、员工个人信息、生产凭据及内部实际底价存入有权限控制的业务系统。
