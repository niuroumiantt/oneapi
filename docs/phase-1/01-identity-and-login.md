# 登录、个人与企业身份

版本 0.2，2026-11-06。本章是设计与官方资料核验；未注册第三方应用、部署身份系统或执行真实登录。详细来源在 [身份来源](06-sources.md#identity)。

## 登录身份、企业关系与业务资格

登录确认用户控制哪个外部账户；内部 user_id 确定本平台账户；Membership 确定这个人可以代表哪个组织做什么。企业资料认证、签约授权、开票资料与信用额度分别管理。

建议同一入口完成自然人登录，然后进入个人工作区或企业组织。企业页面可以提供“创建企业”“接受邀请”“企业单点登录”的入口，但复用同一用户基础。创建企业后可以先预付使用，不能自动得到信用额度。

一个人在本地区可绑定多种登录方式、加入多家公司、拥有个人项目。每个组织的项目、Key、金额、价格权益与成员范围独立。推广员合作资格也不等同平台员工权限；员工入口和权限域独立，强制 MFA。

## 地区页面布局

| 地区 | 建议首屏 | 备用与扩展 |
| --- | --- | --- |
| 中国区，阿里云独立域名 | 微信优先；经验证可用的邮箱恢复/登录入口 | GitHub 开发者入口；手机验证码在短信方案实际接通后启用 |
| 海外区，AWS 独立域名 | Google、GitHub、经验证的邮箱入口 | X 同期纳入适配；实际应用权限和测试通过后显示可用 |

四类提供方都进入研发清单。各自应用注册、域名审核和技术工作可同时开展；某个提供方未获准时不阻塞其他渠道的模型与支付联调。中国区不能只有依赖特定外部网络的登录/恢复路径；目标网络可达性需实测。

首期两区拥有独立的会话、身份数据、应用凭据和回调地址。相同 Google/GitHub 身份可在两区分别有账户；合同、余额、企业成员与优惠不自动复制。未来的跨区账户关联另行定义最小数据流程。

## 各登录渠道怎样认人

| 渠道 | 客户看到的流程 | 服务端的稳定识别依据 | 必须区分的事项 |
| --- | --- | --- | --- |
| 微信网站扫码 | 电脑显示登录二维码，手机微信确认，网页返回 | 该微信应用 AppID 下的 OpenID；来源范围内的 UnionID 可辅助关联 | 网站应用、公众号网页、小程序和支付不是同一集成 |
| 微信内网页 | 微信中打开链接，进入获准的网页授权，再回原页 | 对应网页授权 AppID 下的 OpenID | 实际公众号/应用权限与域名开通需核实；普通手机浏览器给可用备选 |
| Google | 进入 Google 选账户并同意所需资料，返回本站 | 验证 ID token 后使用 issuer + sub | 昵称、邮箱和 Workspace 域不直接授予平台企业权限 |
| GitHub | GitHub 授权必要登录资料后返回 | 授权后 GET /user 返回的不可变 id | 不靠可更改的 username/email，不为单纯登录请求仓库权限 |
| X | OAuth 授权后返回 | OAuth 2.0 + PKCE，GET /2/users/me 的 data.id | 不假设有 OIDC ID token；不依赖一定能取得邮箱 |

微信身份范围见 I01–I04；Google 见 I05–I06；GitHub 见 I07–I10；X 见 I11–I13。微信 UnionID 只在绑定同一开放平台账号的适用应用范围统一，不能裸字符串跨任意主体合并，也不能要求所有登录一定返回 UnionID。

## 一次完整登录的八步

1. 用户在本区域选模型/Agent，也可直接从登录按钮开始；输入促销码可先显示有效性与优惠预览。
2. 服务端建立短期 OnboardingIntent，保存模型、Agent、邀请、促销意图、安全返回路径和区域；不保存第三方密码。
3. 用户点击登录渠道；服务端生成随机一次性 state，并按提供方支持的流程使用 PKCE；OIDC 另验证 nonce。state 只关联服务端事务，不信任 URL 自报折扣和角色。
4. 第三方完成认证并跳回本地区固定回调；服务端验证授权响应、来源、预期客户端、有效期与防重放信息。
5. 读取有来源范围的稳定身份标识，查询 ExternalIdentity。
6. 已绑定则进入原账号；未绑定则完成必要条款与最少资料，创建账号或让用户验证已有账户后显式绑定。
7. 进入个人工作区，或选择/接受邀请进入有权使用的企业；最终计费账户在这里确定。
8. 恢复模型、Agent、促销码和原操作。后端针对选定账户重新核验并兑换优惠；随后生成配置、付款或继续接入。

用户无需每次重新输入已经领取的活动码。登录失败、拒绝授权、二维码过期和支付返回都保留合理有效期内的选择；已确认项目、权益和资金是持久业务记录，不随浏览器会话消失。

## 同一人用不同渠道怎样进入同一账户

外部身份与本区 user_id 采用一对多映射，关键唯一约束是 region + provider_instance + issuer/subject。微信 provider_instance 要区分实际 AppID；UnionID 另保存开放平台来源。

用户先登录原账户，在安全设置中点“绑定另一种登录方式”，近期重新认证原账户，再完成新渠道认证。新身份未绑定其他账户才添加关联，并通知用户；已绑定其他账户则明确提示冲突，不自动移动项目、账本或企业关系。

即使两个提供方返回相同邮箱，也不静默合并。Google 对部分第三方邮箱的验证有边界，GitHub 官方要求用不可变 id；公开邮箱、头像和昵称都不是账户所有权的充分证据。[I06](06-sources.md#identity)[I08](06-sources.md#identity)

企业邀请以管理员发出的指定角色、一次性有效期凭证及被邀请联系方式验证为基础；企业邮箱不自动变成 owner。接受邀请后切换到目标企业，原个人优惠不会自动成为整个企业的价格。

## 账户恢复与安全设置

首期必须有可执行的恢复入口。建议在首次充值或创建正式生产 Key 前，引导绑定可靠联系方式或第二登录方式，避免把所有资金访问依赖在一个第三方渠道上。

解绑要求近期重新认证并保留至少一种可用入口。邮箱/手机号变更有验证、通知和审计；全部入口丢失时使用人工核验与敏感操作保护，不凭昵称或单张支付截图接管账号。会话撤销、MFA、Passkey/口令等能力尽量复用成熟身份系统。

企业 SSO 作为可插拔扩展，由企业配置可信 OIDC/SAML 来源与组织映射后启用。成员离职撤销组织权限；项目服务账户和 Key 按明确所有权与交接规则处理。

## 登录与支付互相独立

GitHub 登录的用户也可以用微信或支付宝付款。收款始终关联已创建订单的 BillingAccount；付款人可能与账户使用者不同，不能凭付款 OpenID 自动合并登录账户。

微信网站登录取得的 OpenID 不能直接假定可用于另一 AppID 的 JSAPI 支付，应按该支付产品的 AppID/商户关系建立付款上下文。[I03](06-sources.md#identity)

## 复用方案与接口边界

业务应用只依赖标准会话、本区 user_id 与明确权限；OAuth 令牌、Web 会话和推理 API Key 分别管理。组织、计费和促销规则不写入提供方资料映射脚本。

Keycloak 继续作为候选核心，但需要验证选定版本：Google/GitHub 有官方社交提供方；微信需要经审查的 broker/适配或支持微信的 CIAM；旧 Twitter broker 已弃用，X 采用官方指南中的通用 OAuth v2 配置并验证。[I14](06-sources.md#identity)

阿里云 IDaaS CIAM 提供微信认证源配置，可作为接入成本的比较候选。选择不同地区身份核心时，业务侧仍保持同一 OIDC/账户映射契约；具体选择在实现前短验证决定，不能同时维护两套重复业务登录逻辑。[I15](06-sources.md#identity)

## 必须验证

同一身份不重复建号、昵称/邮箱变化不丢账户、无邮箱也可按授权范围进入、无 UnionID 不误合并、绑定验证两端、code 重放与 state 错误被拒绝、携码回跳、新老客同规则、企业邀请仅授指定权限、跨地区会话不串用、最后入口不可误删、第三方故障能恢复。
