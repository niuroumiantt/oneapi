# 首期研发与落地优先级 0.3

日期：2026-11-06。状态：设计更新，尚未实现或部署。本页是当前首期范围的入口，取代 0.1 的串行阶段解释；此前 18 个模块仍用于业务划分，不代表开发顺序。

## 本轮已确认的调整

- 五条首期主线：登录与身份；DeepSeek/智谱 GLM 模型广场与 Agent 接入；中国及海外收款；线下促销码、客户折扣与推广返佣；供应商与供应商产品管理。
- 供应主线覆盖获取资源、采购准入、产品和价格、计费对账、资金/权益与容量、需求预测、质量、断线和持续供应。供应商自助入驻可后置，内部供应运营必须首期具备。
- 中国区使用阿里云，海外区使用 AWS，各有独立域名、运行环境及地区配置；核心代码和绝大多数业务模块共用，两区从首期并行建设。
- 首期前台仅两个模型家族入口。全面理解并建档官方模型，按用途和已验证状态渐进展示，不把所有历史型号全部放到首页。
- 客户可先选模型，也可先选自己的 Agent；完成选择后生成适合该客户端的接入配置。
- 有效促销码应在各登录方式下适用，首版允许符合活动规则的新老客户。旧版“新客首次推荐归因”不再作为全部促销的默认限制。
- “trail”暂按 TRAE 理解，正式客户端名称待用户后续纠正；不为此阻塞其他设计。

## 本轮仍属于建议的规则

充值按实际付款记录，折扣作用于适用模型的消费价格；客户优惠与推广佣金分别配置；首版佣金按已收款且已消费的合格净服务金额计提。活动期限、模型范围、折扣、佣金比例、结算周期和金额上限仍待商业确认。

## 目标用户旅程

线下听到促销码或扫描推广二维码 → 查看优惠与模型 → 使用当地可用方式登录 → 进入个人或企业工作区 → 选择模型和 Agent → 领取适用优惠并购买额度 → 生成专属接入配置 → 客户端完成首次真实调用 → 看见费用 → 推广员看见可追溯的佣金进度。

注册、付款和配置应保留同一个 OnboardingIntent：模型、Agent、工作区候选、促销意图及安全返回路径。外部登录或支付回来以后继续原任务。任何 Key、登录令牌、支付机密均不进入推广 URL。

供应运营同时完成另一条路径：发现货源 → 询价和授权核实 → 建采购账户与供应产品 → 测试能力/用量/容量 → 小流量批准 → 支撑客户调用 → 监控与补充资源 → 对账、续约和退出。

## 五条并行工作线与共同底座

| 工作线 | 可以立即并行开展 | 需要共同确定的接口 | 首次验收成果 |
| --- | --- | --- | --- |
| A 登录与身份 | 地区登录页、第三方适配、工作区与邀请、恢复路径 | region_id、user_id、billing_account_id、OnboardingIntent | 各启用方式进入同一预期账户，返回后保留促销和模型选择 |
| B 模型与 Agent | 官方目录快照、模型卡片、客户端模板、协议 PoC | ModelProduct、ModelCapability、AgentConnectionProfile、ApiKey | 两个家族各至少一个获准模型完成真实客户端调用 |
| C 支付与用量 | 订单、地区支付适配、回调、账本、退款 | PaymentOrder、UsageCharge、PriceSnapshot、资金分配记录 | 一笔付款只入账一次，一笔调用费用可解释 |
| D 促销与返佣 | 建活动、生成码与二维码、领取权益、推广员视图 | PromotionRedemption、PromotionEntitlement、CommissionAccrual | 新老客均可按规则领取，真实消费计佣，退款能冲回 |
| E 供应商与供应产品 | 货源准入、采购账户/报价、产品能力、容量与质量、资金预警、采购对账 | SupplierAccount、SupplierModelOffer、SupplyCapacityPool、SupplierRateCardVersion、ProviderAttempt、SupplierBill | 两家族各一条可追溯的获准供应路径，价格/限额清楚，故障与成本可核对 |
| 共同底座 | 阿里云/AWS 环境、域名配置、CI、日志、秘密管理 | 版本化接口与事件、区域策略、发布清单 | 同一应用版本在两区独立部署和回滚 |

五条线的界面可以使用明确标注的样例数据同时开发；金额和权限的领域规则同步实现。供应侧应尽早给出首批实际产品、协议、采购价、容量作用域和错误分类，供模型接入、定价及促销联调使用。对外宣称可用前必须接通真实服务，不能用样例数据通过业务验收。

## 交付节奏按证据推进

| 里程碑 | 同期开展的工作 | 退出条件 |
| --- | --- | --- |
| M0 契约和资格就绪 | 固定共享对象；建两区配置；申请登录/支付应用；核实首批采购条款、价格、限额与客户端协议 | 首发供应路径有明确来源、使用范围、计量及容量依据；身份和商户条件清楚，有可执行验收清单 |
| M1 五条线可交互 | 登录/工作区、广场/接入向导、收银台、促销看板、供应产品/资源/质量后台并行开发 | 客户配置路径连贯；员工能管理供应产品和采购条件；所有模拟状态有标识 |
| M2 完成真实交易与供应闭环 | 两家族、首批 Agent、登录与支付集成；计量/折扣/佣金、采购成本与账单联调 | 真实付款和调用可对账；重试成本保留；退款/佣金更正和获准备援或单源限制通过验证 |
| M3 分地区小流量发布 | 两区独立验收、逐步开放；余额/资源包/容量预警、故障恢复、对账和回滚演练 | 该区域的资格、供应、支付、数据路径和生产质量通过，合同到期或通道退出有处置路径 |

两区研发同时推进；两区商用开放可以在不同日期发生。一个地区的支付或许可尚未就绪时，不拖住共同代码建设，也不借另一地区的商户或接口绕过本区条件。旧版将“美国区工程建设”整体排在 P3 的做法已被本轮替换。

## 首期最小运营后台

优先建设支撑五条主线的操作：登录应用状态、用户与工作区、已验证模型与客户端组合、价格版本、支付订单与退款、促销活动与码、推广归因与佣金、供应商/合同/产品、采购账户与共享容量池、健康与事故、供应账单与差异、异常请求和基本审计。员工先保留供应运营/运维/财务/审核/支持等必要职责。

## 后续再展开

完整企业 PO/合同自动化和账期授信、复杂分销批发与多层渠道、供应商自助入驻、全面 HR、扩展模型家族、高级经营 BI、复杂自动付款。企业工作区、预付支付、必要开票与售后仍进入首期；推迟的是复杂自动化。

## 第一批必须演示的验收场景

1. 新客输入促销码后用微信登录，回跳后优惠和所选模型仍在。
2. 老客改用已绑定 GitHub 登录，账户和额度一致；再次输入同一码不重复发放权益。
3. 未绑定的新社交身份遇到相同邮箱，不自动合并账户；用户通过原账户验证后绑定。
4. 企业成员进入正确工作区；无财务权限的成员输入码后可以提交权益申请，不能擅改组织价格或客户归属。
5. 选择 WorkBuddy 后只展示适用协议与已验证组合；Qoder desktop 和 IDE 分别验证；Cursor Chat/Agent 模式分别标记。
6. 接入向导默认只生成所选模型权限的 Key，可明确选择额外模型；不会把上游 Key 交给客户。
7. 9 折公开价与 6 折专属价采用相同参考基准，显示真正节省的金额，不能误算成 5.4 折。
8. 支付失败、重复回调、跨地区促销码、在途退款、赠送额度消费等不会造成错误入账或计佣。
9. 促销价在一次请求开始时冻结；已消费交易和已领取权益按既定条款处理，后台改价不倒改历史。
10. 两区使用同一发布版本，身份/资金/密钥/原始请求数据隔离；一个区域发布失败可独立回滚。
11. 同一采购账户的多个 Key 按实际限额作用域共享容量，不重复计算；相关上游依赖可识别。
12. 欠费、凭据失效、账户限流和平台过载触发不同处置；HTTP 200 后流中断不能算完整成功。
13. 真实使用量、所有上游尝试成本、供应商账单与充值/付款可核对；探测成本不扣客户余额。
14. 获准备用满足地区、版本、协议、客户数据和预算条件；无合格备用时正确失败，不擅自跨区或换模型。
15. 供应价格、资源包到期、余额数据过期及合同到期分别触发评估，不倒改历史客户价格和权益。
16. 促销发布前能看到预计采购贡献与容量缺口；未实现的供应商返利不当作确定成本减免。
