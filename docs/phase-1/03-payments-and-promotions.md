# 支付、线下促销码与返佣

版本 0.3，2026-11-06。中国区微信/支付宝，海外区信用卡通过 Stripe 等获准商户产品处理。信用卡是付款方式，Stripe 是支付处理服务商；首期建议优先接 Stripe Checkout 的托管收银台。

## 一套业务订单，地区支付适配

| 地区与场景 | 建议支付产品 | 体验与前置条件 |
| --- | --- | --- |
| 中国电脑浏览器 | 微信 Native、支付宝电脑网站支付 | 显示二维码/进入支付宝收银台，后端确认结果 |
| 中国微信内网页 | 微信 JSAPI | 按支付 AppID 获得对应 OpenID，配合已批准商户/应用关系 |
| 中国手机外部浏览器 | 微信 H5、支付宝手机网站支付 | 唤起支付并返回原任务；产品及域名须按实际场景开通 |
| 海外网页 | Stripe Checkout + card | 处理卡支付及需要的验证；其他支付方式按商户支持范围后续启用 |

依据见 [PAY-01 至 PAY-05](06-sources.md#payments)。微信网站登录 AppID 的 OpenID 不能直接假定就是另一支付 AppID 的 OpenID；账户映射与支付身份分别验证。微信与支付宝应用密钥、通知签名、商户号及回调地址均独立保存。

统一 PaymentOrder 保存 region_id、legal_entity_id、billing_account_id、currency、amount、provider、外部支付标识与状态。地区适配器只创建/查询支付、验证通知、退款和获取对账记录；账本和促销规则由共享业务模块执行。

## 支付流程与可恢复状态

1. 客户登录后选择充值金额；页面显示区域、商户、币种、实付金额及适用税费。
2. 服务端创建固定金额的订单，再创建支付会话；重复点击使用业务幂等键恢复同一有效订单。
3. 客户进入相应收银台，完成、取消或失败后都返回可恢复页面。
4. 服务端验证签名、商户/应用、订单、金额、币种及真实付款状态，可靠落库。
5. 业务事务确认订单并写入账本及 Outbox；以订单经济操作唯一键防止不同通知造成重复入账。
6. 前端查询订单状态。遇到回调延迟显示“正在确认付款”，主动查单并后台补偿，不要求客户重复付款。

Stripe Checkout 会话完成不自动等同所有付款方式已到账；消费额度以已确认实付为前提。无付款的赠送权益走独立流程，不能把 no_payment_required 当作现金到账。记录事件 ID 去重之外，也要防止 payment_intent 和 checkout 两类事件重复履行同一订单。[PAY-04](06-sources.md#payments)

退款预留可退实付来源，处理在途请求；退款结果确认后记账，保留支付手续费、争议、已消费服务及上游成本。首期保留可执行的退款、开票与客服路径，复杂税务和应收自动化可后续扩展。

## 线下促销码是首期完整业务链

推广员拥有易口述的促销码、专属链接和二维码。避免大小写歧义及易混字符，复制/扫码/手输最后使用同一服务端规则。不要把推广员身份资料或任何 API Key 放在链接中。

用户可在登录入口、模型报价页或账户优惠页输入；登录入口支持全部启用的身份渠道。登录前只是预校验与临时记住，登录后在选定计费账户上正式兑换。活动可以面向新老用户；是否限制模型、地区、币种、企业合同、使用次数、期限和总预算，由明确的活动规则决定，不能隐含“仅新客”。

促销码属于某个地区活动。跨域访问时可解释当前码的适用地区并提供目标站入口，用户明确选择后再过去；默认不跨区转移余额、登录会话或权益。

## 把“9 折变 6 折”算清楚

以下只是统一口径的例子，不是实际模型价格。若同一参考基准为 100，公开售价 90，促销售价 60，则客户相比本站公开价节省 30，约 33.33%；相对参考基准是 6 折。不能把 90 再乘 0.6 得到 54。

官方参考价只有在同地区、币种、模型版本、输入/输出/缓存维度和税口径可比时才能展示，并保存来源日期。条件不可比时使用清楚命名的本站基准价，不做误导性划线价格。

价格规则至少保存 reference_price_version、discount_basis、rate_or_fixed_price、model_scope、region、currency、valid_from、valid_until、usage_or_discount_cap。模型输入、输出、缓存及附加能力分别定价；“6 折”不默认涵盖所有未来产品。

## 建议首版：优惠作用于消费单价

客户实付 100 元，账本记录 100 元实付额度；符合条件的模型调用按已领取活动的单价扣费。优惠到期后按届时适用价格消费仍未使用的实付额度，页面提前说明期限和范围。这样充值金额、可退款来源和消费折扣各有清楚含义。

暂不同时引入“充值打折”“充值赠送面额”“用量再折扣”三套叠加规则。以后需要额度礼包时单独建产品，不复用为含义不清的一个 balance。

客户确认领取时保存权益条款快照。后台暂停活动可以阻止新兑换；已发放权益的处理遵守发放时条款，不能静默追溯取消。一次请求开始时冻结实际价格、活动权益、计佣规则和采购选择规则。

## 促销归因与客户归属分开

一次活动包含四个独立对象：PromotionCampaign（规则）、PromotionCode（传播入口与推广员）、PromotionRedemption（哪个账户何时兑换）、PromotionEntitlement（兑换后可使用的价格权益）。CommissionRule 独立定义收益。

原有客户的获客归属可保留，新活动记录自己的使用归因。默认只让实际应用到这笔消费的一个活动产生相应推广佣金；输入新码不自动争抢永久客户归属，也不回写已经消费的订单。

同一码重复兑换幂等，切换社交登录方式不会多次领取。同一账户有多个优惠时，向客户展示可用条件和最终采用的方案，不默认叠加；需要替换当前活动时由有权限的客户明确确认。企业约定价格与促销优先级必须按合同执行，不能让普通员工随登录改价。首期建议个人 owner 与企业 owner/billing 管理权益；其他成员可提出申请。

防重范围还包括“本地区计费账户 + 活动 + 权益批次”：同一活动下不同推广员的码不能再次发放同一份权益。合法的重复领取次数按活动规则显式配置；更换推广归因是独立、可审计操作，不通过重新发一份优惠实现。

## 推广收益建议规则

客户折扣率与推广佣金率独立配置。90 与 60 之间的 30 不是自动应付推广员的佣金。

建议计佣基础为已经收款并实际消费的合格净服务金额，排除赠送权益、税款、退款和明确不计佣的商品。每笔用量保存实付/赠送批次分配和活动快照，避免用当前余额倒推历史。

示例：按参考基准 100 的服务促销实付消费 60，佣金率若为 5%，推广员候选佣金为 3；假设采购成本 45、分摊支付成本 1，则本笔贡献为 60 - 45 - 3 - 1 = 11，尚未扣其他运营成本和税费。所有数字仅示范公式，实际比例需成本测算后决定。

充值可以作为推广报表中的转化事件，佣金在符合消费条件后计提。流程为候选 → 待观察 → 可结算 → 审批 → 已付款；退款或拒付产生冻结/冲回/追回记录。首期可以自动计算、人工审核付款，留下凭证；完整自动付款与多层渠道延后。

计佣使用费用行与收益类型等业务唯一键，确保同一 UsageCharge 被重复投递或任务重试时只产生一次原始佣金经济效果；冲回另有业务事件和唯一键。退还未消费本金与退还已消费服务分别处理：充值 100、合格消费 60 产生佣金 3，再退未使用的 40，不自动冲回已完成消费对应的 3。涉及已消费费用的退款/拒付或计佣资格变化，才依据原费用和实付批次分配调整。

## 与供应采购、容量和成本的连接

客户付款余额与上游采购资金分别管理；客户余额充足不代表上游有钱、有适用资源包或有剩余并发。活动发布和大规模推广前检查获准供应、预计负载、资源到期与贡献空间，不能把未达条件的采购返利当成确定折扣成本。

一次客户请求可能产生多个 ProviderAttempt，每次实际采购成本都归入 SupplierCostEntry；未知 usage 进入待核对。客户费用遵守公布规则，平台探测成本不计入客户消费或推广佣金。供方涨价、故障重试或备用通道更贵，不倒改已确认客户价格、已发放权益或历史佣金；按新交易、未来活动和现有条款分别处理。

供应商充值、使用成本、供应账单、付款以及客户退款各自保留证据。客户退款不会自动消除已发生的采购成本。详细规则见 [首期供应管理](07-supplier-operations.md)。

## 首期运营界面

运营活动页：活动名称、地区、模型范围、客户折扣、推广员、佣金率、有效期、每账户次数/额度、总优惠预算、状态和版本。活动发布前预览客户价格、预计成本和收益；达不到规则的组合不能新发布。

推广员页：我的码与二维码、有效兑换数、充值转化、合格已消费金额、待观察/可结算/已付款/冲回佣金。不得暴露客户 Key、提示词、完整实名信息或其他推广员数据。

客户页：已领取权益、适用模型、公开价/专属价、到期日、可用上限和每笔实际优惠。个人与企业工作区分别显示，避免换工作区后误以为仍享有同一权益。

## 发布验收

覆盖各种登录方式携码回跳、新老客、错误/过期/跨区码、重复兑换、邀请进企业、企业权限不足、促销期间换价、优惠上限并发、重复支付、支付回跳丢失、部分退款、拒付、赠送额度不计佣以及佣金付款后退款。

金额和状态采用明确命名：calculateEffectiveModelPrice、redeemPromotionCode、reserveUsageBudget、accrueQualifiedCommission、reverseCommissionForRefund。折扣与佣金不藏在登录回调函数内。
