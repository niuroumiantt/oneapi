# 网关设置与要求登记表

> 这份表登记 semifly.ai 网关（员工调用 `/v1/chat/completions` 走的那一层）**现在每一条设置是多少、写在哪里、是谁定的、对员工有什么影响**。
> 目的是让公司对网关的每一条要求都有明确决定。凡是标 **⚠ 待确认** 的，都是开发时定的默认值，**没有经过负责人确认**；标 **❗ 有问题** 的，是已经发现现行设置有缺陷。
> 核对日期：2026-11-12。代码版本 `6e003b0`，生产镜像 `a00859e`。现行值一栏同时核对了生产数据库和服务器 Caddy 配置。

**来源一栏的含义**

| 标记 | 含义 |
|---|---|
| ✅ 已定 | 有明确依据：负责人提过的要求、官方规则，或实测结论 |
| ⚠ 待确认 | 开发时定的默认值，没有记录理由，没有经过负责人确认 |
| ❗ 有问题 | 现行设置有已知缺陷，需要决定怎么改 |

---

## 0. 请求走的路

```
员工的工具 → Caddy（服务器入口）→ semifly 网关（Node 服务）→ KerAPI → 模型
```

每一层都有自己的限制。一条请求必须同时满足所有层的限制。

## D. 超时与断开

| 编号 | 设置 | 现行值 | 来源 | 对员工的影响 |
|---|---|---|---|---|
| D1 | 单次请求的总时长上限 | **900 秒（15 分钟）**，从发出请求算起，包含流式输出的全过程 | ✅ 已定（2026-11-12 负责人决定） | 够 GLM-5.3 按约 50 Token/秒写满 32K 输出（约 650 秒）；超过返回 504 `upstream_timeout` |
| D2 | Caddy 等网关的时长 | `/v1` 是 910 秒（等到响应头为止），比 D1 多 10 秒，让网关先给出可读的错误 | ✅ 已定（随 D1） | — |
| D3 | 空闲超时（含等第一个字） | **60 秒**：流式请求里上游连续 60 秒没有任何输出就中断。非流式请求在完成前本来就没有输出，所以只受 D1 限制 | ✅ 已定（2026-11-12 负责人决定） | 卡死的流式请求 1 分钟内报错；非流式请求卡死时最长要等 15 分钟 |
| D3a | 超时后员工看到什么 | 还没开始输出：HTTP 504 `upstream_timeout`，不扣额度。流式输出到一半：先收到已生成的内容，再收到一条带 `error` 的数据，之后没有 `[DONE]`；这笔按供应商日志结算 | ✅ 已定（随 D1） | OpenAI SDK 会把这条 `error` 当作异常抛出 |
| D4 | 员工的工具先断开时 | 网关立即关闭上游请求，记为「客户端断开」（`CLIENT_CLOSED`）。还没开始回答就断开的：不扣。输出到一半断开的：等 KerAPI 日志，按日志里的实际 Token 数 × 官方价扣；KerAPI 没收钱就不扣 | ✅ 已定（2026-11-12 负责人决定） | 员工拿到多少付多少，按官方价 |
| D5 | 非员工接口（`/api/*`）| 请求体 16 KB，等待 60 秒 | ✅ 已定 | 只影响网页后台 |
| D6 | 网关自己重启或中断时还没收尾的调用 | 超过 20 分钟仍未收尾、且没拿到 KerAPI 请求号的，记为「网关中断」（`GATEWAY_INTERRUPTED`），不扣，释放预留。拿到了请求号的，按 D4 的规则等日志结算 | ✅ 已定（2026-11-12 负责人决定） | 员工没收到回答就不付钱 |
| D7 | 非流式请求的卡死检测 | 只受 D1 的 15 分钟总时长限制；60 秒空闲超时只对流式请求生效（非流式在回答完成前本来就没有输出） | ⚠ 待确认（2026-11-12 负责人决定先不改，记为待定） | 非流式请求真卡死时，最长 15 分钟才报错 |

**D1、D3 的来历**：原来是 300 秒总时长、没有空闲超时，是 2026-11-10 第一版里开发时写的默认值，没有依据；它和 32K 输出上限矛盾（GLM-5.3 写满 32K 要约 650 秒）。2026-11-12 负责人决定改为 15 分钟 + 60 秒空闲。

**D4、D6 的依据（2026-11-12 核对 KerAPI 日志）**

- 截至核对时，网关记了 223 次调用方先断开（当时错记为 `UPSTREAM_FAILED`，迁移 051 已改为 `CLIENT_CLOSED`），其中绝大多数是一个批量脚本自己的 60 秒超时。
- 同一时段 KerAPI 日志里有 190 条对应的失败记录（类型 5，「status_code=500, upstream error: do request failed」），扣费全部为 0。KerAPI 历史上 234 条失败记录（224 条非流式、10 条流式）没有一条扣费。
- 当时有 30 笔调用因网关发布重启卡住，都没拿到 KerAPI 请求号；按旧规则 24 小时后会按预留上限（合计约 ¥9.7）扣员工。新规则下改为「网关中断」，不扣。

## J. 返回给员工的错误

| 状态码 | 什么时候 | 来源 |
|---|---|---|
| 400 | 请求格式不对（见 B2、B3、B4） | ✅ 已定 |
| 401 | Key 无效或已停用 | ✅ 已定 |
| 402 | 余额不够预留，或 Key 到了消费上限 | ✅ 已定 |
| 403 | 模型未开放，或这把 Key 不允许调这个模型 | ✅ 已定 |
| 413 | 请求超过 8 MB | ✅ 已定 |
| 429 | 超过每分钟次数或并发（**这是我们网关自己的限制，不是 KerAPI 的**） | ✅ 已定 |
| 499 | 调用方已断开（只记在库里，调用方收不到） | ✅ 已定（随 D4） |
| 502 | 上游失败，或上游返回 5xx | ✅ 已定 |
| 504 | 超时：流式 60 秒没有输出，或总时长超过 15 分钟（见 D1、D3） | ✅ 已定 |
| 503 | 模型暂停或没有线路 | ✅ 已定 |
| 上游的 4xx | 原样透传状态码和上游的错误信息 | ⚠ 待确认 |

每个错误都带错误码、请求编号和文档链接；响应头有 `X-Semifly-Request-Id`，成功的调用还有 `X-Semifly-Call-Id`。

## 这份表怎么维护

- 改任何一条网关设置时，同一个提交里更新这份表。
- 每条设置在代码里的位置：
  - 请求限制、频率、并发、超时、计费：`server/src/employee-credit.mjs` 开头的常量和 `/v1/chat/completions` 处理函数。
  - 模型目录、价格、高峰规则：`server/src/official-models.mjs`。
  - 输出保护：`server/src/output-guard.mjs`。
  - 服务器入口：infra 仓库里的 Caddy 配置，`oneapi.glocalstorage.cn` 一段。
  - 按 Key 调高的并发和频率：数据库 `employee_api_keys.max_concurrent`、`per_minute`。
- 员工看到的说明在 `web/docs.js`（`#docs` 页的“限制”和“错误码”），改设置时要一起改。
